# Consents App Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A standalone Twenty app `apps/consents` that stores email consents with a full change history, runs double opt-in with confirmation mails through Brevo, and serves a public preferences page for consents and visible lists.

**Architecture:** Three objects (`emailType`, `consent`, `consentChange`) plus fields on `person` and `messageList`. Logic functions: one authenticated route other apps call to record changes, public routes for confirmation and preferences, database-event triggers that keep `consent.status` equal to the latest change, an hourly cron that retries unsent confirmation mails, and a post-install backfill of preference links. All pure logic (tokens, status rules, grouping, HTML, Brevo payload) lives in `src/utils` with unit tests; Twenty and Brevo calls live in `src/twenty-client` and `src/brevo-client`.

**Tech Stack:** TypeScript, `twenty-sdk` 2.57.0, `twenty-client-sdk` 2.57.0 (`RestApiClient`), vitest, `node:crypto` for HMAC, Brevo REST API v3.

**Spec:** `docs/superpowers/specs/2026-11-14-consents-design.md`

## Global Constraints

- Same toolchain and versions as `apps/nonprofit`: `twenty-sdk`, `twenty-client-sdk`, `twenty-ui` pinned to `2.57.0`, `"twenty": ">=2.57.0"` in `engines`, yarn 4.18.1, Node `^24.5.0 || ^26.5.1`.
- All universal identifiers are valid UUID v4, kept in `src/constants/universal-identifiers.ts` (app, roles, functions) and `src/constants/data-model.ts` (objects, fields).
- File layout per `.claude/skills/develop-app/references/develop-app/app-structure.md`: kebab-case, one export per file, types in `src/types`, helpers in `src/utils/*.util.ts`.
- Application variables: `CONSENT_SIGNING_SECRET` (secret, required), `BREVO_API_KEY` (secret, optional), `SENDER_EMAIL`, `SENDER_NAME`, `ORGANIZATION_NAME` (non-secret). No name starts with `TWENTY_`.
- Public URLs are built as `${process.env.TWENTY_API_URL}/s<path>`, the pattern the form builder uses for `/s/forms/:id`. Never from `RestApiClient.resolveUrl`.
- Confirmation links expire after 30 days. Preference links never expire.
- Status values exactly `PENDING`, `GRANTED`, `WITHDRAWN`. Actions exactly `REQUESTED`, `CONFIRMED`, `GRANTED`, `WITHDRAWN`. Sources exactly `FORM`, `PREFERENCE_PAGE`, `MANUAL`, `IMPORT`, `API`, `BREVO`.
- Public pages and the mail in `nl`, `fr`, `en`; any other language falls back to `en`.
- The app never updates or deletes `consentChange` records.

## Review Focus

1. A person who already has `GRANTED` fills in a form again: status stays `GRANTED`, no mail is sent. Test in Task 3 (`nextStatus`) and Task 5 (route skips sending).
2. A tampered, truncated or expired token, or a preference token used as a confirmation token: a friendly error page, no write. Test in Task 3 (`verifyToken`) and Task 7.
3. Brevo returns 429 or 5xx, or no `BREVO_API_KEY` is set: `confirmationSentAt` stays empty, the route still answers 200, the cron retries. Test in Task 6.
4. Names and texts with `<`, `"` or `&` in the mail and pages: escaped. Test in Task 6 and Task 8.
5. A list whose required email type is withdrawn is posted as checked anyway on the preferences page: membership is left unchanged. Test in Task 8 (`applyPreferences`).
